## 一、上线资源申请及部署（新增）

**目标**：为金融垂直数据（hot_finance 索引）、客户方深度研究流量接入、以及空值率/P95 达标，在 W4 前完成资源申请评审，W7 前环境就绪，W11 灰度、W13 全量上线。

**现状**：生产 gateway 4c8g 无 GPU，与 SearXNG×3 同机；Redis 用外部共享集群（`prism:` 前缀隔离）；ES 3 节点独立集群；crawler 单独容器；代理用 qg.net 短效住宅 IP。

**容量估算与资源申请单（W1 产出，逐项列明数量和理由）**：

| 资源 | 现状 | 申请 | 理由 |
|---|---|---|---|
| K8s namespace 配额 | 无（4c8g 虚机 docker compose） | **共享集群配额 CPU 24c / 内存 48g**（不划独立 node）：gateway 16c32g×1 + SearXNG 1c2g×3 + crawler 2c4g×1 + 后台 0.5c1g×1 + 滚动升级余量 | 运维提供共享集群，不独立划 node；gateway requests 16c32g 由调度器预留，保精排 CPU；余量覆盖后续模型/并发升级 |
| 出口虚机 | 无（forwarder 与 gateway 同机） | **2c4g × 1（有外网权限）** | K8s 容器无外网；gost×3 各绑一个住宅 IP 转发 + 一个通用出口端口（qg.net API/Tier2 API）；需放通 K8s pod → 虚机 8081-8083/18081-18083/8080 |
| ES 集群 | 3 节点 | **沿用现有集群，不新增节点** | hot_finance 年增 ~150GB 由现有集群磁盘余量吸收；W1 用 `_cluster/stats` 核实磁盘/heap 水位，逼近 flood-stage 水位线再单独申请扩容 |
| Redis | 现有外部共享集群 | **配额内存 +1GB** | 配置中心、热配置快照、看板计数、语义近似缓存 key 增长 |
| 代理套餐 | qg.net 短效住宅 | **额度 ×1.5** | 金融快讯 5-10min 高频抓取 + 客户方流量接入；配合迭代项四降本对冲 |
| 网络 | 内网直连 | **内网域名（运维提供）+ HTTPS 证书** | 客户方正式对接入口，替代裸 IP；域名指到集群 ingress |

**目标拓扑**：

```
K8s 共享集群（无外网）                    出口虚机 2c4g（有外网）
┌──────────────────────────┐          ┌───────────────────────────┐
│ gateway ×1（16c32g）      │          │ gost-1/2/3 :8081-8083     │
│ searxng-1/2/3（各 1c2g）  │──内网──▶ │  各绑一个住宅 IP           │──▶ 搜索引擎
│ crawler ×1（2c4g）        │  代理    │ gost API :18081-3 热换 IP  │
│ 后台 ×1（0.5c1g）         │          │ 通用出口 :8080             │──▶ qg.net / Tier2 API
└──────────────────────────┘          └───────────────────────────┘
外部依赖：Redis 共享集群（prism: 前缀） · ES 3 节点集群
```

**部署动作**：
1. W1：容量评估报告 + 资源申请单提交评审（含上述表格 + 不申请的降级方案：reranker 降级 top_k=10、金融只接 5 站点）。申请单定稿前先核实生产真实水位：gateway 用 `docker stats` 采样 CPU/内存峰值，ES 用 `_nodes/stats` 看 heap 压力与磁盘占用，与上表规格比对后确认或微调。
2. W3-W4 **K8s 化改造**：出 K8s manifests——gateway Deployment（`replicas: 1` + readiness 探针 + hf_cache PVC，单副本 + 集群自愈，HA 二期用 Redis 选主锁后再 `replicas: 2`）；SearXNG StatefulSet ×3（实例名/IP 绑定关系须稳定）；searxng settings / gost.yml 转 ConfigMap。**代码改动一处**：proxy_pool 的 `PROXY_FORWARDER_CONFIGS` 写盘恢复改为检测 gost 重连后经 API 重推当前 IP（gateway 与 forwarder 分属集群内外后写不到文件）。
3. W5-W7：集群环境部署 + 出口虚机部署（gost docker compose 照搬现有 `gost/Dockerfile`），预发与生产配置对齐；`OMP_NUM_THREADS=1` 等既有踩坑项写入 Pod env（照抄 deploy.md）。
4. W9：部署架构文档更新（docs/deploy.md 补 K8s 拓扑）、上线检查清单、回滚预案（旧机保留 2 周不下线，域名秒级切回）。
5. W11：灰度（客户方 10% 流量 → 新集群）；W13：全量切换，旧机进入保留观察期。

**结果验收**：W4 资源申请获批（或降级方案确认）；W7 预发环境就绪可压测；W13 全量上线后 2 周内资源水位 CPU < 60%、内存 < 70%，无 OOM/过载事故。

## 二、对接客户方深度研究（新增）

**目标**：Prism 作为客户方深度研究的搜索底座，W3 冻结 API 契约，W7 联调环境可用，W11 灰度上线，W13 全量。

**关键动作**：
1. **W1-W2 需求对接**：与客户方团队确认调用形态——深度研究场景典型特征是 query 长（多约束）、单任务多轮检索（一个研究任务拆 10-30 个 query）、需要正文（NeedContent=true）和引用溯源。明确：QPS/并发目标、top_n 需求（预计 20-50，超出现有默认）、是否用 SSE 流式。
2. **W3 冻结 API 契约**：
   - 专用租户 `partner-tenant`，配额/QPS 按对接结论配置（`scripts/create_api_key.py`）；
   - top_n 上限放开 + `NeedContent=true` 抓正文的墙钟预算单独给该租户调大；
   - 响应增加 `source`/`published_at` 字段保证引用可溯源（复用现有 date_extractor）；
   - 出 API 契约文档（docs/api-reference.md 增补客户方专用说明 + 示例）。
3. **W5-W7 联调环境**：预发环境开客户方租户，提供 mock 数据与回放脚本；客户方侧接入联调，问题清单逐条清零。
4. **W8 联合压测 + 质量联调**：按约定 QPS × 2 压测；用客户方真实任务集（≥30 个研究任务拆出的 query）跑一轮质量评测，问题归入迭代项七处理。
5. **W11 灰度、W13 全量**：灰度期每日对账（请求量/空值率/延迟/客户方侧投诉）。

**结果验收**：契约文档双方确认；压测达到约定 QPS × 2 不触发限流、P95 达标；灰度→全量期间搜索侧 P0/P1 故障 0 起；客户方真实任务集搜索质量 P10 ≥ 75%（深度研究长 query 场景单独口径）。

## 三、金融垂直领域数据源接入与体验优化（需求一）

**技术路线**：复用 crawler 项目「爬虫 → ES → 热路」链路，不在 prism 内另起引擎。crawler 加 spider 写独立索引 `hot_finance`，prism 加金融意图路由。

**接入站点清单（共 10 个，分批）**：

| 批次 | 站点 | 类型 | 调度间隔 | 周次 |
|---|---|---|---|---|
| 第一批（2个） | 财联社电报、东方财富 7×24 快讯 | 快讯 | 5-10 min | W2-W3 |
| 第二批（5个） | 巨潮资讯公告、上交所公告、深交所公告、央行官网、证监会官网 | 公告/政策 | 30-60 min | W5-W6 |
| 第三批（3个） | 国家金融监督管理总局、证券时报快讯、同花顺快讯 | 政策/快讯 | 15-60 min | W10 |

**关键动作**：
1. **W1 spike**：验证财联社/东财/巨潮接口可达性与反爬强度（复用 crawler 现有代理与正文抽取管线），不可达的当场换备选源，W2 开工前站点清单锁死。
2. **crawler 侧**：`hot_finance` 独立索引，mapping 增加 `stock_codes`（证券代码数组）、`doc_type`（announcement/flash/policy/report）；公告保留 400 天、快讯 30 天；复用 ContentFetch → Embed → Dedup → ES 管线，正文抽取失败的条目只留 snippet 不降优先级。
3. **prism 侧（W3-W4）**：金融意图路由——股票代码（6 位数字/SH/SZ）、公司名→证券简称映射表（Redis 维护，纳入迭代项五后台可配）、金融词典（涨停/财报/分红/解禁/研报…约 200 词）；命中 → 热路查 `hot_finance`，未命中走原链路；官方金融源进 `domain:tier:T1`（cninfo/sse/szse/pbc/csrc 等）作冷路 source_trust 加成。
4. **体验**：公告类直达 PDF 原文；结果标来源与时间；实时行情数值**不走 ES**（现有"硬实时数值查询跳过热路"机制继续生效），杜绝陈旧行情。
5. **评测（W4 起每周跑）**：金融测试集 100 query（公告 30/快讯 30/政策 20/研报 20），P10 趋势进看板。

**结果验收**：10 个站点全部入索引且调度稳定（日均有效入库 ≥ 300 条）；金融测试集 P10 ≥ 80%；快讯类查询热路命中率 ≥ 50% 且数据延迟 ≤ 15 分钟；公告类首条官方源比例 ≥ 60%；通用查询 P10 不劣化（回归断言）。

## 四、IP 池冷热时段自定义与降本（需求二）

**关键动作**：
1. **W3 时段表**：新增配置 `PROXY_SCHEDULE`（如 `peak=08:00-22:00,offpeak=22:00-08:00`，支持多段三档 peak/normal/offpeak），纳入热配置。
2. **分档策略**：高峰巡检 15s、剩余有效期 <20% 提前热切、备用 IP 抽 2×；低谷巡检 120s、仅"近 10 分钟有真实流量才探"（现有机制保留）、备用 IP 减半、按 deadline 自然过期不提前换。
3. **W6 流量自适应**：近 10 分钟 QPS 滑动窗口动态修正档位（低谷 QPS 突增自动升档，升档响应 < 1 分钟），避免固定时段表被突发流量打穿。
4. **成本埋点（W6）**：每次抽 IP 记录数量/时段到 `dashboard:proxy_cost:*`，看板出"额度消耗/日/时段"曲线，W8 起每周对比降本效果。

**结果验收**：低谷时段代理额度消耗下降 ≥ 40%（W8 vs W3 两周看板对比）；升档响应 < 1 分钟；高峰空值率不因降本劣化（红线：< 0.1%）。

## 六、数据统计看板优化（需求四）

**关键动作**：
1. **W5-W6 指标采集扩展**（在现有 `dashboard.py` 基础上新增）：空值率（result_count=0 单独计数 + DropTrace 归因：引擎层空 vs 闸门杀空）、Tier2 兜底触发率与花费、代理成本（迭代项四）、分租户用量、P50/P95/P99 延迟分位。

**结果验收**：上述指标一屏可见，排查问题不再先翻日志文件；告警 MTTD ≤ 5 分钟（W6 后用一次真实故障或演练验证）。

## 七、搜索结果质量：P10 相关性 ≥ 80%（需求五）

**关键动作**：
1. **W2 评测基线**：评测集扩容至 300 query（现有长尾集 + 金融 100 + 客户方长 query 30 + 导航类 50），每条标注期望域/意图；跑一轮基线 P10 并记录，之后每周五回放一次出趋势。
2. **W4-W6 已知失分模式清零**（按 CONTEXT.md 失分清单逐个过）：
   - 导航意图：域名-品牌词拼音/缩写映射表 + ICP 备案库轻量 source gate，首条准确率 50% → 80%；
   - 长复合词误杀：jieba 自定义词典 + 同义归一（"个人所得税"≈"个税"），消除对杀空保护的依赖；
   - 字典/百科残留："非释义 query 降权纯释义页"规则落地（CLAUDE.md 已预留未做）。
3. **W9 reranker 阈值再标定**：基于 300 query 回放分数分布重校准 FLOOR/MARGIN/COLLAPSE 三阈值（配合迭代项五热配置，标定完直接后台下发）。
4. **自动断言**：已确认失分用例 100% 进 `replay_testset.py` 断言，每周回归全绿才合入排序相关改动。

**结果验收**：W13 评测集 P10 ≥ 80%；导航类首条准确率 ≥ 80%；失分用例回归断言全绿；P10 周趋势曲线连续 3 周 ≥ 80%（不是单次达标）。

## 八、系统稳定性：空值率归零（需求六）

**关键动作**：
1. **W2-W3 换 IP 联动清挂起**：代理刷新成功回调中同时清 SearXNG `suspended_times`（复用现有"清引擎熔断"回调），消除"干净 IP 被挂起跳过"窗口；冷启动/换 IP 后探针查询验证出网再放流量。
2. **W4-W5 多级兜底链固化**（任何路径不返回空数组）：Tier1 → Tier1 剩余引擎换 query 变体重试 → ES 热路 → Tier2 付费兜底 → 语义近似缓存（cos≥0.92 的同义 query 历史结果，仅非实时意图）→ 降级返回 top3 弱相关 + `degraded=true` 标记。
3. **W6 起空值归因周报**：result_count=0 强制写 DropTrace 全链路裁决，每周一复盘 Top 归因并逐个清零，直至周新增归因为 0。
4. **W11 混沌演练**：杀代理池/停 1 个 SearXNG 实例/断 ES 三种故障注入，验证兜底链与告警。

**结果验收**：W9-W13 连续 4 周空值率 < 0.1%（目标 0）；降级返回占比 < 1%；混沌演练空值率峰值 < 1% 且 5 分钟内自愈；Tier2 兜底月花费 ≤ 预算上限。

## 九、性能优化：P95 9~10s → ≤ 4s（补充保留项）

**关键动作**：
1. **W1 归因**：用 timing.log 分阶段耗时统计 P95 构成占比（SearXNG 单引擎 5s 超时打满 / reranker CPU 0.5~1.5s 串行 / CAPTCHA 重试 / 抓取），出归因报告，按 Top 大头排优化顺序。
2. **W4-W5 引擎层**：慢引擎动态降权/熔断（按看板存活率与延迟）；单引擎超时 5s 分档（历史快的引擎 3s 截断）；超时引擎不阻塞主链路。
3. **W5 墙钟预算硬执行**：`SEARCH_TOTAL_BUDGET_S` 到点返回当前最好结果 + `partial=true` 标记。
4. **W9 并行化**：L3 精排与正文抓取并行、粗排 top-K 提前送精排，流水线重叠代替串行。
5. **W7-W13 热路扩容**：金融索引进热路（迭代项三）+ 客户方高频 query 沉淀，热路命中占比 ≥ 30%（热路 ≤500ms 直接拉低整体 P95）。

**结果验收**：W8 P95 ≤ 6s；W13 P95 ≤ 4s、P99 ≤ 8s；超预算截断请求占比 < 5%（不靠大量截断造假达标）。

- **资源审批（迭代项一）是客户方上线与 P95 达标的前置依赖**：若 W4 未获批，启用降级方案（reranker top_k=10、金融先接 5 站点、客户方 QPS 目标减半），W2 同步通知客户方侧。

- **降本与稳定性权衡**：低谷降档以"空值率不劣化"为红线，两项指标同屏监控。
- **reranker 不换模型**：4c8g/8c16g 无 GPU，v2-m3 已否决，质量缺口用阈值标定 + 特征增强补足。
